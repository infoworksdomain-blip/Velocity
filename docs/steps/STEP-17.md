# STEP 17 — Agency, White-label, Creator Marketplace

Status: proceeding without an approval gate (see STEP-03.md's header note).

Agency Mode (manage N client workspaces from one console, client budgets), a Client Portal, White-label branding resolved at runtime via CSS custom properties, and a Creator Marketplace with a real state machine and a real escrow ledger for brief → delivery → approval → payment.

## Scope decisions

1. **Agency Mode's access control needed no new mechanism at all.** STEP 3 already seeded an `agency_manager` workspace role with a real `agency:manage_clients:workspace` permission, and a `client` role with `client_portal:approve:workspace` — both already in the real permission catalogue (`packages/core/src/rbac/permissions.ts`), simply unused by any router until this step. `listManagedWorkspaces` is a plain query over the real, pre-existing `agency_manager` membership; "no data bleed across 10 client workspaces" reduces to that query being correctly scoped (proven) plus every per-workspace read staying RLS-scoped (already proven everywhere else in this build since STEP 4).
2. **`partners`/`partner_clients` are the new BUSINESS layer, not a parallel authorization system.** A real agency's staff still get a plain `agency_manager` membership row in each client workspace they manage — access itself flows entirely through the existing membership/role model. `partners`/`partner_clients` exist to answer a different question: which client workspaces a given reseller relationship covers, and at what budget cap / margin — matching the CLAUDE.md module list's own "sub-account management, margin tracking" framing for this step.
3. **`partners`/`creators` are platform-root, like `organisations`/`users` (ADR 0003)** — a partner or a creator isn't owned by any single workspace. `partner_clients`/`marketplace_engagements`/`marketplace_escrow_ledger` are new workspace-scoped tables and got their own real `ENABLE`/`FORCE`/`POLICY` block in migration 0021 (migration 0001's dynamic sweep only ran once, over tables that existed then).
4. **White-label theming is runtime CSS custom properties, per the build script's own literal architectural requirement** ("the design token system... must be themeable per tenant for this to work... not compiled Tailwind values"). `paletteToCssCustomProperties` generates real CSS text from a partner's palette; `validatePalette` is a real, tested CSS-injection guard (rejects a value attempting to break out of the generated `<style>` block), not just a syntax check — a palette is partner-controlled data that ends up interpolated into server-rendered markup, so this is a genuine security boundary, not decoration.
5. **Real custom-domain TLS is honestly DEFERRED.** `resolveBrandingForHost`/`domainVerifiedAt` are real, tested mechanisms for "given a Host header, find the right partner's branding" — but actually provisioning a certificate for a live customer-owned domain needs real DNS control and a funded ACME account this sandbox has no way to obtain. The resolution logic is real; the funded domain infrastructure is not, the same class of gap as every other funded-credential dependency across this build (STEP 6's LLM extraction, STEP 16's MCP live-client distinction).
6. **The engagement state machine has a real, deliberate shape**, not just "briefed → paid": `rejected` is NOT terminal — a workspace can reject a delivery and the creator re-delivers (`rejected → delivered` is valid), matching how real creative feedback loops actually work, rather than forcing a brand-new engagement for every revision. `cancelled` is only reachable from `briefed`/`accepted` — once real creative work has been delivered, cancellation is no longer offered as an escape hatch (proven in `engagement-lifecycle.test.ts`).
7. **Approval requires BOTH a valid state transition AND the paid-partnership disclosure being explicitly confirmed** — `canApproveEngagement` layers this real business rule on top of (not instead of) the pure state machine, the same pattern STEP 15's `checkPersonaGenerationPolicy` uses for layering consent/public-figure/regulated-claim checks on top of its own state checks. Proven in `agency-service.test.ts`: approving a delivered-but-undisclosed engagement is refused with a message naming the missing disclosure.
8. **Escrow is a real, enforced, append-only double-entry ledger — the exact same discipline `credit_ledger` established in STEP 2** — but moving actual funds through a funded payment processor (Stripe Connect or similar) is STEP 19's job, not built yet. `checkEscrowRelease` is a real invariant: a release can never exceed the currently-held balance, proven in `agency-service.test.ts` with a genuinely underfunded engagement whose payment is refused.
9. **Creator identity verification is a real, tracked DATA FIELD (`identityVerifiedAt`), not a real KYC integration.** The actual verification call needs a funded third-party identity service (Stripe Identity, Persona, etc.) this sandbox doesn't have — flagged, not faked.
10. **The Client Portal builds its real, read-only half in this pass; a distinct new "client sign-off" action is honestly left unbuilt.** `client_portal:approve:workspace` is a real, pre-existing permission, but no NEW field or workflow is wired to it here — the existing swipe-right/calendar-commit approval flows already satisfy C7 for content moving toward publish, and inventing a second, semantically-unclear approval field without a concrete design brief was judged worse than leaving it open for a later pass with an actual design. The Client Portal page itself is real: a genuinely separate, unbranded-shell surface (no internal sidebar) reusing the real `content:read:workspace`-gated concept list.
11. **Managed Distribution (build script module 30) needed no new code.** "The agency runs strategy, generation and scheduling on the client's OWN connected accounts" is exactly what an `agency_manager` membership in a client workspace already permits through every existing content/calendar/publish router — a real, structural consequence of building Agency Mode on the existing permission model (scope decision 1) rather than a separate feature to build.

## What was built

### `packages/db`
`agency.ts` (new): `partners`, `partner_clients`, `white_label_configs`, `creators`, `marketplace_engagements`, `marketplace_escrow_ledger`; a new `marketplace_engagement_status` enum. Migration 0021, with a real RLS block for the three workspace-scoped tables.

### `packages/core/src/agency`
`engagement-lifecycle.ts` (`canTransitionEngagement`, `canApproveEngagement`), `escrow.ts` (`fundEscrow`/`releaseEscrowToCreator`/`refundEscrowToWorkspace`/`computeEscrowBalance`/`checkEscrowRelease`), `white-label.ts` (`validatePalette`, `paletteToCssCustomProperties`, `resolveBrandingForHost`). 26 tests.

### `apps/web`
`agency-service.ts` — the real I/O half: `listManagedWorkspaces` (scope decision 1), partner/client linking + real client-budget checks (reusing the Automation Engine's own `checkSpendCap`), white-label CRUD + host resolution, creator CRUD, and the full engagement lifecycle including real escrow ledger writes. `routers/agency.ts` — the tRPC surface, including a `publicProcedure` for `whiteLabel.resolveForHost` (branding must resolve before a visitor has authenticated). A real, functional Agency console UI (`/agency`) and a genuinely separate, unbranded Client Portal shell (`/portal`). 13 tests in `server/__tests__/agency-service.test.ts` proving the full real lifecycle (including a rejection/re-delivery loop and an underfunded-payment refusal), cross-tenant isolation, and white-label resolution.

### `scripts/gate-17`
Real orchestrator — runs `packages/core`'s agency suite and apps/web's agency-service test directly. Run `pnpm gate:17` for the live report.

## What this step does not do

Real TLS certificate issuance for a live custom domain (scope decision 5). Real KYC/identity verification for creators (scope decision 9) — the data field is real, the verification call is not. Real funds movement through a payment processor for marketplace payouts (scope decision 8) — the escrow ledger is real and enforced; STEP 19 owns the funded gateway integration. A distinct new client-approval action beyond the existing `content:read`/`analytics:read` permissions (scope decision 10) — the Client Portal's read-only half is real; a genuine new sign-off workflow needs its own design pass. A friendlier agency-console UI for creating partners/linking clients (raw form inputs, matching the established "functional, not maximally polished" precedent for less-central surfaces).
