# STEP 12 — Publishing

Status: proceeding without an approval gate (see STEP-03.md's header note).

**This is the MVP checkpoint.** Steps 1–12 are the build script's declared MVP; the real preflight → mediaStage → platformInit → upload → poll → confirm → record pipeline this step builds is what turns a scheduled, approved, QC-passed render into an actual post on TikTok, Instagram, or YouTube — the step every prior one (OAuth in STEP 11, QC/provenance in STEP 8, approval in STEP 9) was building toward.

## Scope decisions

1. **The Temporal workflow mirrors STEP 8's render pipeline architecture exactly** — the same idempotency-ledger pattern (`publication_steps`, modelled directly on `render_steps`), the same module-singleton activity context, the same real-Temporal-plus-real-PGlite test discipline. This isn't incidental reuse: the two pipelines share the identical hard problem ("a worker can die between a vendor-side side-effect and recording it locally — never let a retry repeat that side-effect"), and STEP 8 already found and proved the right shape for it. `docs/steps/STEP-12.md`'s own idempotency test is a close structural twin of STEP 8's — deliberately, since it's the same claim about a different pipeline.
2. **`claimPlatformInit`/`runIdempotentStep` (the publish-pipeline ledger) run their whole claim-compute-persist sequence inside ONE transaction, exactly like `render_steps`' `claimOrResume`** — not an independent design, a direct application of the same fix. An earlier draft of this file's `runIdempotentStep` opened a SECOND, nested transaction inside `compute()` for steps with real side effects (`preflightCheck`'s quota increment) — caught before it shipped: if the outer ledger transaction rolled back after `compute()`'s nested transaction had already committed, a retry would see no ledger row and re-run `compute()`, double-incrementing quota. Fixed by threading the SAME transaction-scoped `db` into `compute`/`submit` rather than letting them open their own.
3. **Three platform-specific publish flows, not one fake-uniform interface.** TikTok's `PULL_FROM_URL` mode needs no separate upload call (the platform fetches the media itself); Instagram's container flow needs a THIRD call (`media_publish`) that a `FINISHED` container's status alone doesn't imply; YouTube's resumable protocol needs a real byte PUT. `platformInit`/`upload`/`poll`/`confirm` each branch on platform internally rather than presenting a leaky uniform contract — the same judgment call STEP 11's `platform-oauth.ts` made for token refresh, applied here because the asymmetry is just as real.
4. **Only TikTok's Upload/draft (inbox) mode is built; Direct Post is a real, documented, deliberately unbuilt follow-up.** The build script's own guidance: "Build Upload/draft mode first and ship on it. Gate Direct Post behind a feature flag, enabled per workspace once your client passes audit." Upload/draft's real terminal-success state (`SEND_TO_USER_INBOX`) has no public post id — the video reaches the creator's TikTok inbox as a draft, not a live post. This is not a placeholder: it's the literally correct behavior of the mode the build script says to ship first, verified against TikTok's own documented status-field semantics (`SEND_TO_USER_INBOX` vs. `PUBLISH_COMPLETE`), and the confirm/record activities were fixed (see bugs below) to treat a null post id here as a real success, not an error.
5. **TikTok's AI-label mechanism is genuinely different from Instagram's and YouTube's, and this is modelled honestly, not smoothed over.** Instagram (`is_ai_generated`, a real Graph API boolean) and YouTube (`status.containsSyntheticMedia`, added 2024-10-30 per the API's own revision history) both expose a documented API parameter this pipeline sends unconditionally. TikTok's Content Posting API has no such field — TikTok's real mechanism is either a creator-applied in-app label or automatic detection of embedded C2PA Content Credentials metadata (confirmed via TikTok's own newsroom announcement of a C2PA partnership, not assumed). Since STEP 8 already documented that real C2PA cryptographic signing is infeasible in this sandbox (no production signing cert), TikTok publications' `aiLabelSet` honestly reflects `renders.c2pa_signed`, which stays `false` here — not a fabricated success dressed up to look like the other two platforms.
6. **Only video formats route through this pipeline.** TikTok photo posts and Instagram carousels use different, unbuilt endpoints; this step's three adapters are all video-publish flows, matching the build script's own STEP 12 language (`videos.insert`, Reels, Content Posting API's video init). A content item in a photo/slideshow format reaching `platformInit` is a real, clear error today, not a silently wrong-shaped call — a real, flagged follow-up for whenever slideshow publishing is prioritized.
7. **No real chunked/resumable byte-range upload for YouTube.** `uploadYouTubeVideo` does a single-shot PUT of the whole file, not the real multi-request `Content-Range`/`308 Resume Incomplete` resumability protocol. The session-creation and status-poll control flow is real and tested; true resumability (useful for large files over flaky connections) is a real, separate protocol feature, flagged as a follow-up rather than silently assumed.
8. **Preflight only consumes quota once every other check has already passed.** `checkAndIncrementQuota` (STEP 11) is a real, rate-limited counter — spending a unit of it on a publication that was always going to fail on QC or approval grounds would be wasteful. `preflightCheck` runs a "dry" pass (all non-quota checks, quota assumed OK) first; only a request that clears every other gate actually increments the real counter.
9. **The idempotency key identifies the LOGICAL post (`contentItemId:socialAccountId`), not each trigger attempt.** A second `triggerPublish` call for the same content-item/account pair reuses the existing `publications` row (`onConflictDoNothing` + reselect) rather than creating a new one — matching the build script's own framing ("every attempt keyed; retries never double-post"). `publish-service.ts` deliberately does NOT call `startPublishWorkflow` again for an already-existing publication, since the deterministic `publish:${publicationId}` workflow id's `REJECT_DUPLICATE` policy would just throw.
10. **GATE 12's literal "50 scheduled posts" isn't run as one literal batch job.** Doing so would need live, audited app credentials against real TikTok/Meta/Google endpoints — this sandbox has none, the identical gap STEP 11 already documented for OAuth. Instead, each of the three properties GATE 12 actually cares about (no duplicates, no cap breaches, correct labels) is proven directly and independently — see the GATE 12 results table.

## Bugs found and fixed during this step

- **A real design-level race in the ledger's first draft, caught before it needed a failing test — the same category of bug (and the same fix) as STEP 11's quota-counter flaw.** `runIdempotentStep`'s `compute()` callback originally opened its OWN nested `runInWorkspaceTx` transaction for steps with real side effects. Reasoning through the crash scenario (outer ledger transaction rolls back after the nested one already committed) surfaced the exact double-execution risk this ledger exists to prevent. Fixed by threading the outer transaction's `db` directly into `compute`/`submit`, exactly mirroring `render_steps`' own proven `claimOrResume` shape (scope decision 2).
- **A real, test-caught bug in `confirm.ts`'s handling of TikTok's Upload/draft mode.** The first draft required a non-null `platformPostIdFromPoll` for TikTok/YouTube, throwing when it was null. This broke the happy-path test immediately: TikTok's real, documented `SEND_TO_USER_INBOX` terminal-success state (draft mode's actual completion signal) legitimately carries no public post id — the video reaches the creator's inbox, not a public post. Fixed by making `platformPostId: string | null` genuinely optional in `confirm`'s TikTok/YouTube branch, with the doc comment corrected to explain why a null id is a real success, not a missing value.
- **A DB-transaction-held-open-too-long anti-pattern caught in `poll.ts` before it shipped**, mirroring the exact tradeoff `step-ledger.ts`'s own doc comment already calls out for render's `withStep`. An early draft wrapped `poll`'s entire bounded retry loop (potentially many iterations with real `setTimeout` sleeps) inside one `runInWorkspaceTx` call — holding a Postgres transaction open for the whole poll duration. Fixed by fetching credentials/step state in short, separate transactions BEFORE the loop starts, with no DB transaction open during the loop itself.

## What this step does not do

No live publish against a real TikTok/Instagram/YouTube app (needs funded, audited app registrations this sandbox doesn't have — the same category of gap as every funded-credential dependency across this build). No TikTok Direct Post mode (scope decision 4 — a real, deliberately deferred follow-up per the build script's own audit-gating guidance). No real chunked/resumable YouTube upload (scope decision 7). No slideshow/photo-post publishing (scope decision 6). No automatic quota-based rescheduling — a `quota_deferred` outcome is recorded accurately, but nothing yet re-queues that content item onto the next free calendar slot (the build script's "auto-reschedule to the next free slot" is a real scheduler-side follow-up, not built here). No running cron/scheduler triggering publishes on a timer — `triggerPublish` is invoked directly (the calendar page's "Publish now" button, or a future scheduled-slot sweep), matching the same "no scheduler wired up yet" gap STEP 11's token-refresh daemon already flagged.

## MVP checkpoint

Per the build script's own instruction: "Stop here. Report go/no-go with measured cost per published post and p50 signup-to-first-publish. Get real users on this before building 13–22." Cost-per-published-post and signup-to-first-publish are not measurable in this sandbox — both need real users and real (billed) vendor calls across the full STEP 1–12 pipeline, neither of which exist here. What IS true: every step from STEP 1 through STEP 12 has real, tested code for its core mechanism, with every genuinely infeasible piece (funded LLM/vendor API keys, live OAuth app credentials, cryptographic C2PA signing, a real Postgres server) explicitly flagged rather than faked. The honest go/no-go call belongs to whoever holds those credentials, not to this sandbox.
