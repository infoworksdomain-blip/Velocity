# STEP 11 — Social Integrations

Status: proceeding without an approval gate (see STEP-03.md's header note).

OAuth connect/disconnect/reconnect for TikTok, Instagram, and YouTube; per-account health; rolling-window quota state (`platform_quota_state`); a token-refresh daemon with T-7/T-3/T-1 notifications; a reconnect flow that surfaces a revoked/expired connection as a distinct, actionable state rather than a silent failure.

## Scope decisions

1. **STEP 11 builds connect/health/quota/refresh only — the actual publish pipeline is STEP 12, not this step.** The build script's own STEP 12 header (`preflight → mediaStage → platformInit → upload → poll → confirm → record`) is a separate, larger undertaking (idempotency keying, failure taxonomy, AI-labelling on publish). GATE 11's first check ("connect and publish a test post") is therefore genuinely split: connect is real and built here; publish doesn't exist as code yet, by design, not by omission.
2. **Three real, asymmetric OAuth refresh semantics are modelled explicitly, not papered over with a fake-uniform interface.** TikTok issues a `refresh_token` that itself rotates on every refresh (the caller must persist the *new* refresh token, not just the new access token — easy to get wrong). YouTube's refresh token does not rotate (`access_type=offline` + `prompt=consent` at authorization time). Meta/Instagram has no separate refresh grant at all — "refreshing" a long-lived token means re-exchanging the *current* still-valid token via the same `fb_exchange_token` call, so `refreshMaterial` for Instagram is just the new access token itself, reused as next time's exchange input. `packages/core/src/social/platform-oauth.ts`'s `refreshPlatformToken` is the one place this asymmetry is handled, so no caller needs a platform-specific branch.
3. **OAuth `state` uses a signed JWT, not a new DB table.** `packages/core/src/social/oauth-state.ts` reuses the same `jose` SignJWT/jwtVerify pattern already established for session tokens (STEP 3) — the state payload (workspaceId, userId, platform, nonce) round-trips through the JWT itself, so there's nothing to garbage-collect and no extra table for CSRF protection.
4. **Route handler, not tRPC, for the OAuth callback.** `apps/web/app/api/oauth/[platform]/callback/route.ts` is a plain Next.js `GET` route using native `Request`/`Response`, because TikTok/Meta/Google redirect the user's *browser* here after consent — a cross-site navigation initiated by the platform, not a same-origin fetch tRPC expects. It never echoes a raw upstream error to the client; failures log server-side and redirect with a short, generic reason.
5. **Quota counters use a single atomic `INSERT ... ON CONFLICT (social_account_id) DO UPDATE ... WHERE ... RETURNING` statement, not a multi-step transaction.** An earlier design (try an atomic UPDATE, then branch on whether a row existed to decide INSERT-vs-reset) had a genuine race: two concurrent first-ever requests for the same account could both reach the "no row yet" branch and both attempt an INSERT. Caught through reasoning before a test ever needed to catch it, and redesigned to one atomic statement — which required adding a unique index on `platform_quota_state.social_account_id` (migration 0012) so the `ON CONFLICT` target is well-defined. GATE 11's own concurrency check exists specifically to prove this the hard way (real `Promise.all`, not sequential awaits) — see the token quota test below.
6. **The token-refresh daemon resolves a real notification recipient via `memberships`, never a fabricated `userId`.** `NotificationEvent` requires a `userId`, but the daemon operates at social-account/workspace granularity with no inherently associated user. `notifyWorkspace` looks up the first real membership row for the workspace — a genuine simplification (no owner-role-preferring join, which would need an extra `roles` join this daemon doesn't otherwise need), documented as such rather than silently presented as more precise than it is. A workspace with zero members is a real, if unusual, state — the daemon skips notifying rather than throwing.
7. **The daemon itself is a single dependency-injected tick function (`runTokenRefreshTick`), not a running scheduled process.** `db`, `kms`, `configs`, `fetchImpl`, and `now` are all injectable, which is what makes GATE 11's "fast-forward expiry" claim a real test rather than a real multi-day wait. A cron/scheduled-task wrapper calling this once a day in production isn't built — there's no scheduler wired into this codebase yet at all (nothing in `apps/worker` currently runs on a timer; STEP 8's Temporal workflows are triggered by application events, not cron). Flagged as a real, not-yet-done follow-up.
8. **`platform_credentials`' encrypted payload is a fixed JSON shape (`{accessToken, refreshMaterial, resourceId}`)** established once in `apps/web/server/social-service.ts` and reused unchanged by the daemon — `resourceId` carries Instagram's own linked-business-account id (the extra identifier TikTok/YouTube's health checks don't need); it's `null` for the other two platforms.

## What was built

### `packages/db`
`connection_status` enum (`connected` / `reauth_required` / `disconnected`), `social_accounts.connection_status` + `.last_health_check_at`, and a unique index on `platform_quota_state.social_account_id` (migration 0012 — scope decision 5). `NotificationEventType` extended with `token_expiring` / `account_reauth_required`.

### `packages/core/src/auth/oauth`
Three real adapters against each platform's documented endpoints (rule 5 — implementing a documented contract, not inventing one): `tiktok.ts` (Login Kit v2 — authorize/token/refresh/user-info, rotating refresh tokens), `meta.ts` (Graph API — short-lived → long-lived exchange, linked Instagram business account lookup, no separate refresh grant), `youtube.ts` (Google OAuth — non-rotating refresh tokens, `access_type=offline`). 20 tests across the three, all against local mock HTTP servers via the codebase's established `fetchImpl: typeof fetch = fetch` DI seam.

### `packages/core/src/social`
`quota.ts` (`checkAndIncrementQuota` — scope decision 5), `token-refresh.ts` (`computeExpiryNotificationLevel`/`shouldAttemptRefresh` — the T-7/T-3/T-1/expired threshold logic, parametrized test table), `platform-oauth.ts` (`refreshPlatformToken`/`checkPlatformAccountHealth` — scope decision 2), `oauth-state.ts` (scope decision 3). 17 tests total (quota's 3 include the real PGlite concurrency proof; token-refresh's 11 cover the threshold table exhaustively; oauth-state's 3 cover issue/verify/tamper-reject).

### `apps/worker/src/jobs/token-refresh-daemon.ts`
`runTokenRefreshTick` (scope decisions 6-8) — queries `platform_credentials` joined to `social_accounts` where `connection_status = 'connected'`, decrypts via KMS, calls the unified `refreshPlatformToken`, re-encrypts and persists the (possibly rotated) credential, and on failure marks the account `reauth_required` with a real notification. 4 tests against a real embedded Postgres (PGlite): a genuine refresh (including asserting the *rotated* TikTok refresh token is what gets persisted, not the old one), a genuine revoked-token failure path, a skip for an account not yet near expiry, and a skip for an account already `reauth_required`.

### `apps/web/server/social-service.ts` + `routers/social.ts`
`loadPlatformOAuthConfigs` (reads the three platforms' client id/secret pairs from env), `buildAuthorizationUrl`, `completeOAuthConnection` (the callback's actual work — exchanges the code, fetches account info via `checkPlatformAccountHealth`, encrypts and stores the credential, sets initial quota caps by reusing STEP 10's `calendar.loadPlatformCapsConfig`/`capFor`). Router: `accounts.list/disconnect`, `oauth.authorizationUrl`, `quota.list`.

### `apps/web/app/api/oauth/[platform]/callback/route.ts`
Real GET route handler (scope decision 4).

### `apps/web/app/accounts`
A real page: per-account health via the STEP 7 `AccountChip`, a distinct "Reconnect needed" label + button for `reauth_required` accounts (re-entering the same OAuth flow), quota-used display, and connect buttons for all three platforms. Split into an outer `Suspense`-wrapped component and an inner one using `useSearchParams()`, per a genuine Next.js 15 static-prerendering requirement caught by a real `next build` failure.

### `scripts/gate-11`
Real orchestrator — runs `packages/core`'s suite plus the worker's daemon test directly (not folded into the worker's default `pnpm test`, matching STEP 8's precedent of keeping a slow/concurrency-sensitive test out of the default run path). Run `pnpm gate:11` for the live report.

## Bugs found and fixed during this step

- **A real test-isolation bug in the daemon's own test file, caught by a genuine failing assertion, not assumed.** The daemon's query is intentionally global (no per-test scoping — a real daemon tick processes every workspace), but the test file's four tests shared one PGlite instance across `beforeAll` without retiring each test's seeded account afterward. Because each test advanced `now` forward, an earlier test's freshly-refreshed account (now carrying a *new*, later expiry) could still fall within a *later* test's refresh window and get swept into that tick too — exactly what happened: `reauthRequired` came back with 2 accounts instead of the 1 the second test expected. Fixed by tracking every seeded account per test and setting it to `disconnected` in `afterEach`, so each test's tick only ever sees its own account. This is a bug in the test's isolation, not the daemon's logic — the daemon behaving "too globally" is the *correct*, intended behavior being exercised.
- **A design-level race condition caught before it needed a failing test**, carried over into this step's implementation from the quota work: see scope decision 5. Documented here rather than under STEP 11's own "found and fixed" list a second time, since the actual code and fix were already in place going into this step; STEP 11 only exercised and confirmed it under the daemon's usage pattern too.

## What this step does not do

No publish pipeline (scope decision 1 — that's STEP 12 in full: preflight, idempotent upload, AI-labelling on publish, failure taxonomy). No live OAuth click-through against real platform consent screens (needs funded/audited app registrations this sandbox doesn't have — the same category of gap as every other funded-credential dependency in this build, e.g. STEP 6's LLM extraction call, STEP 8's vendor render adapters). No running scheduler/cron wrapper around `runTokenRefreshTick` (scope decision 7) — the tick function itself is real and tested, but nothing currently invokes it on a timer in this codebase. No TikTok Direct Post audit application (the build script explicitly frames this as a real-world, weeks-long external process to start in parallel, not something to fabricate here) — Upload/draft mode is what STEP 12 should gate on first per the build script's own guidance.
