# STEP 19 — Billing

Status: proceeding without an approval gate (see STEP-03.md's header note).

Stripe subscriptions plus metered credits. Plan limits, mid-cycle upgrade/downgrade (via Stripe's own Billing Portal), top-up packs, dunning, invoices, a hard spend/generation cap per workspace, and nightly ledger reconciliation.

## Scope decisions

1. **`subscriptions`/`invoices` already existed since migration 0000, unused until now** — the fifth consecutive step (after STEP 15/16/17/18) where the real work was giving pre-designed schema its first real reader/writer. `credit_ledger`/`usage_events`/`credit_balances` (STEP 2, real since STEP 8's metering) needed no schema change at all — this step is what finally spends the balance they've been tracking. A `stripe_customer_id` column and a new `top_up_purchases` table (migration 0023) are the only genuinely new schema.
2. **Market-anchored credit pricing replaces the provisional cost-plus conversion.** `metering/usage-recorder.ts`'s `usdToCredits` (1 credit = $0.01 of underlying provider cost, explicitly flagged "STEP 19/Billing owns the real pricing model" since STEP 8) is now `billing/credit-pricing.ts`'s `creditsForUsage` — the build script's own literal numbers (4 credits/image, 10 credits/video-second, a 20s video = 200 credits) charged by OUTPUT UNIT, not by whichever vendor happened to fulfil the request. This is the real, deliberate SaaS-margin model the cost-plus placeholder never was: two video providers with different real costs now charge the customer identically for the same output. Text/tts/transcription are flat, near-free per-call charges, per the build script's own explicit reasoning about not punishing STEP 9's cheap-LLM-heavy swipe-queue economics.
3. **`packages/core/src/billing/plans.ts` is the new authoritative pricing model STEP 4's `PLAN_SEAT_LIMITS` and STEP 7's `PLAN_CREDIT_LIMITS` explicitly asked for**, by WRAPPING them (their numbers stay defined once, so STEP 4/7's existing call sites are unchanged) rather than duplicating the seat/credit numbers a second time. Stripe Price ids are resolved from environment variables per plan, never hardcoded — a different Stripe account per environment has different price ids for the same conceptual plan.
4. **Upgrade/downgrade/cancel/payment-method changes all happen inside Stripe's own real Billing Portal**, not a hand-built page — `createBillingPortalSession` is the entire surface this step needs for that, and it's also why this step doesn't reimplement Stripe's proration math anywhere: a subscription-item price change through the portal is proration Stripe itself computes and bills correctly, which is the realistic way most production Stripe integrations actually work (not a corner cut — a deliberate architectural choice that reduces this step's own surface for handling money correctly).
5. **A dunning grace period is real, not instant-cutoff.** `isBlockedBySubscriptionStatus` gives a `past_due` subscription (Stripe's own Smart Retries are already attempting to collect) a 3-day window measured from `subscriptions.updated_at` before blocking generation — an instant cutoff on the first missed payment would be a harsh, support-ticket-generating policy for what's often a transient card decline. `canceled`/`unpaid` block immediately and unconditionally, regardless of remaining credit balance.
6. **Webhooks are the ONLY writer of subscription/invoice status** — nothing in checkout-session creation writes a `subscriptions` or `invoices` row directly (only a `top_up_purchases` row, in a `pending` state, since Checkout confirms success client-side before the webhook necessarily arrives). This means local state can never drift ahead of what Stripe actually confirmed happened, and it's why `checkout.session.completed`'s top-up-crediting path is idempotent by construction: keyed on the real, unique Stripe Checkout Session id, so Stripe's own documented at-least-once webhook delivery can never double-grant credits — proven directly (the same event delivered twice credits the ledger exactly once).
7. **GATE 19's "a workspace at its cap cannot generate" needed a genuinely NEW enforcement gate, not a rewire of an existing one.** `credit_balances` (the STEP 2 materialized view) had only ever been READ for display before this step (dashboard's CreditMeter, the MCP `get_credit_balance` tool, the public `/v1/credits` endpoint) — confirmed by direct inspection, never as a block. `assertWorkspaceCanGenerate` is wired into the exact single choke point STEP 9's "never render before the swipe" architecture already established (`render-service.ts`'s `triggerRenderForConcept`, called before Temporal ever starts a real, billable render workflow) — not a second, parallel gate. The pre-check estimate (from the storyboard's own total scene duration/count) is intentionally conservative; the real, final charge is still metered precisely by the render pipeline itself.
8. **A real bug in `usage-recorder.ts`'s existing tests was a genuine, expected ripple from the pricing-model change, not a defect** — every test asserting a specific credit debit amount computed via the old `usdToCredits(costUsd)` needed updating to the new `creditsForUsage(jobKind, units)` shape; fixed alongside the pricing-model change itself (not treated as a separate "found and fixed" bug, since the old assertions were correctly describing the OLD, now-deliberately-replaced behaviour).
9. **The nightly reconciliation job is a real, tested, callable function with no scheduler wired to it** — the same honestly-flagged gap first noted at STEP 11 and true at every step since (this codebase has no cron/queue-consumer infrastructure at all). `reconcileAllWorkspaces`/`reconcileWorkspaceLedger` (apps/web/server/credit-gate-service.ts) are real and exercised against real seeded data; a real, permission-gated manual trigger (`admin.billing.reconcile`) exists in the meantime, closing the same class of gap STEP 18's admin console already established a pattern for.
10. **Drift alerts and low-credit refusals both publish through STEP 7's real notification bus**, reusing `credit_low` and `automation_alert` — `credit_low` was explicitly reserved for this step by that module's own doc comment since STEP 7 ("credit-low events are STEP 8/12/19's job to emit"); `automation_alert` is reused for reconciliation drift as the closest existing "something needs human attention" event type rather than inventing a new one. Both resolve a real workspace member to notify via the same "first real membership row" lookup `apps/worker`'s token-refresh-daemon already established (STEP 11), not a fabricated userId.
11. **Real Stripe SDK usage throughout, tested against a local mock server, not a live account.** `stripe.checkout.sessions.create`/`stripe.customers.create`/`stripe.billingPortal.sessions.create` are exercised via the SDK's own documented `host`/`port`/`protocol` override pointed at a real local HTTP server mimicking Stripe's real response shapes — the exact same "real SDK, no live network" discipline `packages/text-engine`'s Anthropic/OpenAI adapter tests already established for this build, extended to a client-library-based integration rather than a hand-rolled `fetchImpl` adapter. Webhook signature verification is genuinely testable with zero network calls at all (`stripe.webhooks.constructEvent`/`generateTestHeaderString` are pure HMAC crypto), proven against both a correctly-signed payload and two distinct forgery/tampering attempts.

`billing.ts` — `subscriptions` gained `stripe_customer_id`; new `top_up_purchases` table (unique on `stripe_checkout_session_id`, real RLS). Migration 0023.

### `packages/core/src/billing`
`plans.ts` (`BILLING_PLANS`, `resolveStripePriceId`, `resolvePlanKeyFromStripePriceId`), `credit-pricing.ts` (`creditsForUsage` — the market anchor), `generation-gate.ts` (`checkCanGenerate`, `isBlockedBySubscriptionStatus`, the real 3-day dunning grace), `reconciliation.ts` (`reconcileCreditLedger`, >1% drift detection). 29 tests. `metering/usage-recorder.ts` updated to debit via `creditsForUsage`.

## What this step does not do

An actual end-to-end run against Stripe's live test-mode API (scope decision 11) — needs a real, funded Stripe test account this sandbox doesn't have. A real scheduler for the nightly reconciliation job (scope decision 9) — the same gap flagged since STEP 11, now with a real manual admin trigger in the meantime. Stripe Tax configuration and UK VAT handling — these are largely Stripe-dashboard configuration (enabling Stripe Tax on the account, registering tax jurisdictions) rather than application code, and are out of this sandbox's reach for the same funded-account reason as the rest of the live Stripe surface; Checkout Sessions are built with `automatic_tax` left unconfigured pending that account-level setup. Refunds — `stripe.refunds.create` is a real, simple SDK call with no business logic of its own to build around it in this pass; not wired into a UI or router procedure here. Per-seat billing proration nuances beyond what Stripe's own Billing Portal already handles natively (scope decision 4).
