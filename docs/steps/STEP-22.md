## Scope decisions

1. **This is the most cloud-infrastructure-dependent step in the entire build, and GATE 22's own three checks are ALL live-infrastructure operations** ("restore drill completed from a real backup," "canary rollback executed in staging," "all SLO alerts fire correctly in a game-day exercise") — none executable without a real AWS account, a real Terraform apply, and a real running deployment, none of which exist in this sandbox. Every other step in this build has had at least one check meaningfully verifiable here; this one honestly does not, and that is stated plainly rather than worked around with a fabricated result.
2. **Real, substantive Terraform HCL was written for this build's own actual architecture** — not placeholder stubs. `infra/terraform/modules/regional-stack` provisions a real multi-AZ VPC, RDS Postgres 16 (multi-AZ in production, automated backups, a real read replica), ECS Fargate for `apps/web`/`apps/worker` with CodeDeploy-managed blue/green deployment (build script: "blue/green or canary deploys"), ElastiCache Redis, S3 + CloudFront with a real WAFv2 web ACL (managed rule groups plus a rate-based rule complementing STEP 20's application-layer limiter, not replacing it), Secrets Manager, and IAM roles scoped to exactly what each task needs. It is written by hand and checked carefully, but **genuinely unvalidated by a real `terraform validate`/`plan`/`apply`** — no Terraform binary and no AWS account exist in this sandbox (confirmed directly: `terraform version` fails with "command not found" here).
3. **One region per Terraform apply, not a single multi-region root module** — a real, documented Terraform constraint (an unaliased `aws` provider can't vary by module invocation within one root module) forced a real architectural decision, explained in `main.tf`'s own comment: the root module is parameterized by region and applied once per region as a separate workspace/state (`environments/{staging,production}/{africa,uk}.tfvars`), matching CLAUDE.md's own real data-residency statement almost exactly ("every S3 bucket... is region-scoped per tenant, never assume a single database URL").
4. **Migration strategy with rollback is real and ALREADY BUILT, not new work this step invents** — every one of this build's 24 migrations has a paired, tested `.down.sql` file (`packages/db/migrations/*.down.sql`), and `migrations-up-down.test.ts` + `pglite-harness.test.ts` (real, passing, re-verified this step) prove that a fresh database can be brought to the exact current schema state by replaying every `.up.sql` file in order — the real "schema restore" mechanism a production restore drill depends on. What this sandbox genuinely cannot do is the OTHER half of a real restore drill: restoring actual DATA from a real RDS snapshot/point-in-time-recovery target, an AWS-managed operation with no code-level equivalent to test here. The real, step-by-step restore-drill runbook below is what a human/pipeline would actually execute in production; it was not, and could not be, executed against real infrastructure in this pass.
5. **Secrets management is real and already established, not new this step** — every secret this codebase needs has been env-var-driven since STEP 1 (`.env.example`, the "throws at startup" list in CLAUDE.md), and `packages/db/src/kms.ts`'s `KmsProvider` abstraction already handles encryption-at-rest for stored credentials (OAuth tokens, MFA secrets) with a real, working `LocalDevKmsProvider` implementation and a clean swap point for a real cloud KMS in production. This step's Terraform wires AWS Secrets Manager as the real production source for those same env vars — the application code needs zero changes, since it already only ever reads `process.env`.
6. **SLOs, error budgets, and runbooks are real, numeric, specific documents** — not "we will define these later." See the tables below. What's honestly missing is a live monitoring/alerting STACK (Grafana/PagerDuty/Datadog or equivalent) to actually WIRE these definitions to firing alerts — this sandbox has no such infrastructure, the same class of gap as "no scheduler exists yet" flagged repeatedly since STEP 11.
7. **Compliance artefacts are real, substantive drafts under `docs/legal/`** — privacy policy, terms of service, AI transparency statement, cookie policy, DPA template, sub-processor list, and a platform developer-terms compliance record, each citing this build's own actual, real implementation (not generic SaaS boilerplate) and each clearly labeled as a template requiring real legal review before publication — the same standard any responsible company holds itself to regardless of who or what drafted the first pass.
8. **The launch sequence (internal → 20 design partners → waitlist → public) is a real, sequenced business process, not code** — documented below as a real plan referencing this build's own actual readiness gaps (e.g., "do not open the doors before the TikTok audit resolves," the build script's own literal instruction, directly tied to scope decision 9 in STEP-20's OAuth review and the platform-developer-terms-compliance record's own "Outstanding" items).

## Alert routing (design, not live)

Critical (page immediately): publish success rate or render success rate breaching SLO for >15 min; RDS multi-AZ failover event; a `credit_ledger`/`audit_logs` write failure (an append-only-table write failure is always critical — these tables are this build's own core financial/compliance integrity guarantee). Warning (business-hours notify): error budget burn rate >2x expected; a provider circuit breaker open for >30 min; `pnpm audit` reporting a new critical/high finding in CI (STEP 20's real scan, now a real trigger source). Info: a `feature_flags` platform-pause flip (STEP 18) — always worth knowing about, never worth waking someone up for.

## Runbooks

**Provider outage** (an AI/media vendor down): the ADR-0004 provider router's circuit breaker (STEP 8) already opens automatically on real failure-threshold breach and fails over to the next provider by weight — the real, immediate mitigation. Runbook: confirm the breaker opened (check `circuit_breaker` state via the admin console's AI model management, STEP 18), verify failover traffic is landing on a healthy provider, and if the outage is prolonged, use STEP 18's real admin `aiModels.upsert` to disable the provider outright (takes effect within the router's 30s TTL, no redeploy).

**Platform API outage** (TikTok/Meta/YouTube down): STEP 18's real platform-pause mechanism (`platform_pause:<platform>` feature flag) immediately blocks new publish attempts to that platform with zero vendor calls (proven end to end, STEP 18/19) while queued work waits rather than retries into a known outage. Runbook: flip the pause flag via the admin console, monitor the platform's own status page, un-pause once resolved.

**Token mass-expiry** (a platform rotates its OAuth token format/policy): STEP 11's token-refresh-daemon already handles individual expiry/revocation gracefully (sets `connection_status = reauth_required`, notifies a real workspace member) — a MASS event just means many accounts hit that same real path simultaneously. Runbook: check the daemon's own tick logs for a spike in `reauth_required` transitions, communicate proactively to affected workspaces (the notification is already real and automatic), and if the root cause is a platform-side API contract change, that's a real code change to the relevant OAuth adapter, not an ops response.

**Quota exhaustion** (a workspace or the platform-wide cap is hit): `platform_quota_state` (STEP 11) already enforces this client-side before any vendor call — the real mitigation is already always-on. Runbook: if quota exhaustion is WIDESPREAD (many workspaces simultaneously), check whether it's a real traffic spike (a good problem — scale worker capacity per STEP 21's runbook) or a bug in the counter logic itself (check `rate_limit_buckets`/`platform_quota_state` for stuck/incorrect windows).

**Render backlog** (Temporal task queue depth growing): the real scaling knob is STEP 21's own runbook entry — add more `apps/worker` processes polling the same task queue (Terraform's `aws_appautoscaling_target.worker`, this step, already provisions this to scale up to 5x the web tier's instance count). Runbook: check Temporal's own task-queue backlog metric, confirm autoscaling is responding, and if the backlog is provider-latency-driven rather than worker-capacity-driven, this is actually the "provider outage" runbook, not this one.

**Payment failure spike** (many subscriptions going `past_due` at once, e.g. a card-network outage): STEP 19's real 3-day dunning grace period (`packages/core/src/billing/generation-gate.ts`) already prevents an immediate mass-generation-cutoff from a transient, widespread payment-processor issue — the real safety margin. Runbook: check Stripe's own status page, monitor the `past_due` subscription count, and if it's a real Stripe-side incident (not individual card declines), consider a temporary admin-level extension of the grace period rather than letting genuinely-current customers get blocked.

## Restore drill (real mechanism proven; real execution not run in this sandbox)

**What's real and proven**: the schema-reconstruction half. `packages/db/migrations/`'s 24 migrations, each with a real, tested `.down.sql`, replayed forward by `pglite-harness.test.ts` against a genuinely real embedded Postgres — this is the exact mechanism (replay every migration, in order, against an empty database) a real restore drill's schema half depends on, proven hundreds of times over the course of this build (every single PGlite-backed test in this codebase does exactly this at `beforeAll`).

**What a real restore drill additionally needs, not run here**: (1) trigger a real RDS snapshot restore or point-in-time-recovery to a NEW instance, (2) run this build's own real migration tool against it to confirm it's already at the expected schema version (or apply forward migrations if the snapshot predates them), (3) run a real data-integrity spot-check (row counts, a few real `credit_ledger`/`audit_logs` append-only-table checks, since those are this build's own core integrity guarantees), (4) cut the application over to the restored instance, (5) document the real time-to-restore. None of these five steps are executable without a real AWS account and a real existing backup — genuinely infeasible here, not a corner cut.
