# STEP 7 — Design System + Dashboard

Status: proceeding without an approval gate (see STEP-03.md's header note).

## Scope decisions

1. **Fonts**: Appendix A specifies a licensed geometric grotesque (Aeonik) or free alternatives (Satoshi/General Sans/Geist). None of these are pre-installed, and sourcing/self-hosting real font files is a licensing and asset-pipeline decision, not a component-architecture one. `--font-display`/`--font-mono` tokens are defined now with strong system-font stacks standing in for the real typeface, so every component is already wired to the token rather than a hardcoded family — swapping in real font files later is a one-line change in `tokens/index.css`, not a per-component rewrite.
2. **No pre-built `dist/` for `packages/ui`.** CSS Modules need to be processed by whatever bundler ultimately consumes them (Next's webpack for `apps/web`, Vite for Storybook) — pre-compiling with `tsc` alone doesn't touch `.css` files at all. `packages/ui`'s package.json points `main`/`types` at source, `apps/web` adds it to `transpilePackages`, and Storybook (Vite-based) transforms it directly. This is the standard pattern for an internal monorepo UI package and avoids a second, redundant build step.
3. **All 28 components from Appendix A.5 are built**, per GATE 7's literal requirement ("Storybook covers every component in Appendix A §4"). Several (`BlitzCard`, `CalendarSlot`, `TimelineEditor`, `SafeAreaOverlay`) are presentational only — their real interactive behavior (swipe physics, drag-to-reschedule, timeline scrubbing) belongs to the steps that own that logic (STEP 9, STEP 10, STEP 8B.7) and is not invented here. Building the component's visual shape now, wired to real props and real tokens, is STEP 7's job; wiring it to real state machines is those steps' job.
4. **Every Dashboard field is a real query against a real table — revised from the original plan.** The original plan for this decision was to have `dashboard.get` return hand-typed placeholder numbers with a `TODO(STEP-N)` comment per field. Once `content_concepts`, `calendar_slots`, `social_accounts` and `metric_snapshots` turned out to already be schema-complete (STEP 2), a hardcoded placeholder would have been *less* honest than just querying them: a fresh workspace with no producers yet (STEP 8/9/10/11/12/13 haven't shipped) genuinely has zero Blitz-pending concepts, zero upcoming slots, zero connected accounts and zero metrics, so the real query and the "placeholder" would return the same zero — except the real query stays correct automatically once those steps ship, where a hand-typed placeholder would need to be found and deleted. `creditBalance` reads the real `credit_balances` materialised view (STEP 2); `creditLimit` is a new, explicitly-provisional `PLAN_CREDIT_LIMITS` constant in `packages/core/src/plans/credit-limits.ts`, mirroring the same disclaimer already on `PLAN_SEAT_LIMITS` (STEP 19/Billing owns the real numbers). `nextBestAction` is computed from a fixed priority order over this same real state — never fabricated to manufacture a suggestion.
   - This also surfaced a real prerequisite gap: nothing yet let the browser discover which workspace to even ask about. Added `workspace.listMine` (user-scoped, not workspace-scoped — it's how the client finds a workspace id in the first place) and fixed the vanilla tRPC client (`apps/web/lib/trpc-client.ts`), which had no mechanism to send a dynamic `x-workspace-id` header. Both were required for any workspace-scoped procedure — not just `dashboard.get` — to be callable from the browser at all; STEP 4/5 built the pieces but never closed this loop.
5. **Notifications (7.3)**: the bus (`packages/core/src/notifications/bus.ts`) and schema (`notifications` + `notification_preferences`, migration `0006_notifications`) are real, including RLS (both tables are workspace-scoped, so both get `ENABLE`/`FORCE ROW LEVEL SECURITY` + the `workspace_isolation` policy, per migration 0001's own note that later tenant tables must add this themselves) and the standard grant. There are no real event producers yet (render-complete, publish-failed, etc. don't exist until STEP 8/12), so the bus is proven with 4 synthetic-event unit tests (`packages/core/src/notifications/__tests__/bus.test.ts`) rather than an end-to-end producer path. `apps/web/server/notifications-bootstrap.ts` wires the bus to persistence via `subscribeAll`, lazily, the same singleton-on-first-import shape as `getAdminDb()`.

## What was built

- **Token additions**: `--font-display`, `--font-mono` (system stacks, see decision 1), full per-scale tracking/line-height tokens matching Appendix A.3's type table exactly, plus `--scrim`, `--on-dark`, `--text-stat`, `--text-wordmark` added while building components (see "bugs found" below).
- **`packages/ui`**: real React + TypeScript + CSS Modules component library, 28 components (see list below), each with a Storybook story. Storybook configured with the Vite builder (verified installable in this environment before committing to it, same diligence as STEP 6's Playwright check).
- **Token audit script** (`packages/ui/scripts/audit-tokens.mjs`): scans every `.tsx`/`.css`/`.module.css` file outside `packages/ui/tokens/` for hex colors, `border-radius`/`box-shadow` literals, and raw `font-size` px/rem values not going through a token — fails with a report of file:line offenders. Wired as `pnpm --filter @velocity/ui audit-tokens` and into GATE 7.
- **tRPC client fix** (`apps/web/lib/trpc-client.ts`, `apps/web/lib/workspace-context.tsx`): `currentWorkspaceIdRef`, a module-level ref kept in sync by a `useEffect` in `WorkspaceProvider`, read by `httpBatchLink`'s `headers()` callback to send `x-workspace-id` dynamically — the vanilla client had no way to do this before, so no workspace-scoped procedure was actually callable from the browser.
- **`workspace.listMine`** (`apps/web/server/routers/workspace.ts`): user-scoped query returning the workspaces a user belongs to — the WorkspaceSwitcher's data source and the thing that lets the Dashboard auto-select a workspace on first load.
- **Dashboard** (`apps/web/app/dashboard/page.tsx` + `apps/web/app/dashboard/dashboard.module.css` + `server/routers/dashboard.ts`): pending-Blitz count, upcoming scheduled posts, last-7-day performance, credit balance + limit, connected accounts, next-best-action — every field a real query (see decision 4). Widget order differs by `workspaceType`: `business` leads with next-best-action/accounts/performance; `individual` leads with the credit meter.
- **`packages/core/src/plans/credit-limits.ts`**: provisional `PLAN_CREDIT_LIMITS`, following `seat-limits.ts`'s own "STEP 19 owns the real numbers" disclaimer. `packages/core/src/plans/index.ts` now barrels both files; `packages/core`'s root export was repointed from `./plans/seat-limits` to `./plans/index`.
- **Notifications**: `packages/core/src/notifications/bus.ts` (typed pub/sub — `publish(event)` / `subscribe(eventType, handler)` / `subscribeAll(handler)`), migration `0006_notifications` (`notifications` + `notification_preferences` tables, both RLS-protected), `apps/web/server/notifications-bootstrap.ts` (bus → persistence wiring), `apps/web/server/routers/notifications.ts` (`list`, `markRead`, `preferences.get/update`).

### Bugs found and fixed during verification

- **Flaky bcrypt test timeout under parallel-package load** (`packages/core/src/auth/__tests__/password.test.ts`). Running `pnpm test` across all 9 packages concurrently (rather than `@velocity/core` in isolation, which had always passed) put enough CPU contention on the bcrypt (`SALT_ROUNDS=12`) hash/compare calls that one test exceeded vitest's 5000ms default timeout — a genuine flake, not a logic bug: the same 4 tests passed individually in every prior step's isolated run. Fixed by raising the per-test timeout to 20000ms for these 4 tests specifically, with a comment explaining why — not by lowering `SALT_ROUNDS`, which would trade real password-hashing security for test speed. Re-ran the full 9-package suite after the fix: all tests pass, individual bcrypt test durations 2.3–5.8s, comfortably under the new timeout.
- **Masked exit code on the first full-suite run**: piping `pnpm test 2>&1 | tail -200` reports the exit code of `tail` (always 0), not `pnpm`/`turbo` — the first run's background-task notification said "exit code 0" while the log it summarized actually ended in `ELIFECYCLE Test failed`. Caught by reading the actual log content rather than trusting the notification summary; re-ran with the exit code captured explicitly (`pnpm test > log 2>&1; echo EXIT_CODE=$?`) for the real pass/fail signal.
- 4 hardcoded design-token violations caught by `audit-tokens.mjs` while building components (`AccountChip` font-size, `StatCard` font-size + a hardcoded green that also violated the flare-only accent rule, `FAQAccordion` font-size, `SiteFooter` font-size) — all fixed before this GATE 7 run, listed here for the record since they were real bugs the audit script was built to catch.

## What this step does not do

No real font files (decision 1). No Blitz swipe physics, calendar drag-to-reschedule, or timeline scrubbing behavior (decision 3 — STEP 9/10/8B.7 own those). No Dashboard data beyond what's already real in the schema — Blitz queue, scheduling, social accounts and analytics stay at zero until STEP 8–13 ship producers (decision 4). No real notification producers (decision 5). No dark-mode toggle UI (the token values exist from STEP 1; wiring a user-facing toggle is a small follow-up, not blocking this gate). Dashboard p75 render time under realistic load is unmeasured (no seed data generator yet).
