# STEP 18 — Admin

Status: proceeding without an approval gate (see STEP-03.md's header note).

User management (search, suspend, audited impersonation), workspace management, AI model management (enable/disable providers, routing weights, cost ceilings, per-model kill switch), content moderation, social integration management, fraud/risk detection, feature flags evaluated per workspace and per user, audit log viewer, and system health/support tooling.

## Scope decisions

1. **Almost every table and permission this step needed already existed, unused, since STEP 1/STEP 3.** `feature_flags`, `moderation_reviews`, and `risk_signals` were all created in migration 0000, and `users:suspend:platform`/`workspaces:manage_any:platform`/`moderation:review:platform`/`feature_flags:manage:platform`/`system:configure:platform` were all seeded onto `superadmin` (and partly onto `support`/`moderator`/`finance`) since STEP 3's real permission catalogue — this is the fourth consecutive step (after STEP 15/16/17) where the actual work was giving pre-designed, unused schema and permissions their first real reader/writer, not inventing new authorization from scratch. `audit_log:read:platform` is the one genuinely new permission this step adds — none of the existing ones covered read-only platform-wide oversight.
2. **STEP 3's impersonation flow needed zero new backend code.** `routers/auth.ts`'s `admin.impersonate` mutation already wrote both a real `impersonation_sessions` lifecycle row and a permanent, audited `audit_logs` entry, gated on `users:impersonate:platform` — confirmed by direct inspection, not assumed. This step's `/admin` page is simply the first UI surface that could trigger it; the audited flow itself was already complete.
3. **Feature flags evaluate per workspace AND per user via a real 4-tier precedence** (`packages/core/src/admin/feature-flags.ts`), extending STEP 4's workspace-override → organisation-default → platform-default settings resolution one level further: an exact workspace+user match wins over a user-only override, which wins over a workspace-only override, which wins over the platform default. This required one new nullable `userId` column on `feature_flags` (migration 0022) — the existing `workspaceId` column was already there. Feature-flag reads always use the admin (RLS-bypassing) connection: a platform-default row has `workspace_id IS NULL`, and `feature_flags` already carries RLS from migration 0001's dynamic sweep (it existed in migration 0000) — under a tenant-scoped session, `workspace_id = current_setting('app.workspace_id')::uuid` would make a NULL-workspace global row invisible, since `NULL = anything` is never true in SQL. Feature flags are platform-controlled config an app already parameterizes explicitly by workspaceId/userId, not tenant-owned secret data, so reading them via the admin connection carries no cross-tenant leak risk.
4. **The "social integration global pause" reuses feature flags rather than new infrastructure**, via a `platform_pause:<platform>` convention key (`platformPauseFlagKey`/`isPlatformPaused`) — a global row (workspaceId and userId both null) is the only tier that can ever answer an unscoped pause check. This is wired into `packages/core/src/publish/preflight.ts`'s real preflight checks (a new `platformPaused: boolean` input field), so a pause takes effect on the very next `preflightCheck` call — no TTL, no cache, immediate — proven end to end through a real publish workflow run in `publish.workflow.preflight-failures.test.ts` (real Temporal + real PGlite), including that it produces zero vendor calls, the same "never even reach the vendor" discipline STEP 12 already established for every other preflight rejection.
5. **AI model management is the DB-backed `ProviderConfigSource` STEP 8's own `config-source.ts` doc comment explicitly reserved for this step**, plus the TTL-based auto-reload GATE 18's "60 seconds without a deploy" literally requires. Two new platform-root tables (`ai_provider_configs`, `ai_router_settings`, migration 0022), seeded with the EXACT current values from `config/providers.json` — proven equal by a real test (`db-provider-config-source.test.ts`), so switching from the file source to the DB source changes nothing on cutover. `DbProviderConfigSource` (in `apps/worker`, not `packages/providers` — see decision 6) is a real OVERRIDE layer: a DB row overrides only the admin-controllable fields (enabled/weight/tiers/adapter/breaker); a provider with no matching row keeps the file's own values untouched, and credentials are NEVER duplicated into the DB — `ai_provider_configs` has no credentials column at all, so an admin console built on this table can never expose or edit a raw API key.
6. **`DbProviderConfigSource` lives in `apps/worker`, not `packages/providers`.** `packages/providers` has no `@velocity/db` dependency, and adding a DB-specific implementation there would break its DI-seam layering — the interface (`ProviderConfigSource`) belongs in the package; the concrete DB-backed implementation is wired at the app boundary, the same split this codebase already draws between `withWorkspace`/`getAdminDb()` (app layer) and the service functions that only depend on a generic `Database` type.
7. **`ProviderRegistry` gained a real TTL-based auto-reload** (default 30s, comfortably under GATE 18's 60s bound), with an injectable clock so `registry.test.ts` proves the exact reload boundary — config served stale one tick before the TTL, re-read exactly at/after it — without a real wall-clock wait, the same fast-forwarded-`now` discipline STEP 11's token-refresh-daemon test already established. `reload()` still exists for an explicit, immediate re-read (used by the DB source's own tests); the TTL is what makes an admin's change propagate automatically, with no external scheduler and no process restart.
8. **Render/publish-workflow tests unrelated to STEP 18 stay pointed at the plain file source.** Wiring `getProviderRegistry()` to `DbProviderConfigSource` by default would have made every existing `render.workflow.*`/`publish.workflow.*` test transitively require a live admin DB connection just to construct a registry, for pipeline tests that have nothing to do with STEP 18's admin overlay. `apps/worker/src/temporal/activities/context.ts` gained a swappable, test-sticky `ProviderConfigSourceFactory` (not reset by `resetActivityContextForTests`, unlike the per-request `runInWorkspaceTxImpl` override); `useRealProviderConfigForTests()` (already called by every render/publish workflow test file) now also points it at a plain `FileProviderConfigSource`. STEP 18's own DB-overlay/TTL behaviour is proven directly by `registry.test.ts` and `db-provider-config-source.test.ts` instead — a real, deliberate test-scope boundary, not a gap.
9. **`preflightCheck`'s new platform-pause read needed its own admin-DB accessor in `apps/worker`.** The activity layer had no `getAdminDb()`-equivalent before this step (only `runInWorkspaceTx`, which requires a workspaceId and enforces RLS) — `context.ts` gained one, matching apps/web's `getAdminDb()` naming and behaviour (lazy singleton, real network Postgres in production, swappable via `setAdminDbForTests` for the four `publish.workflow.*.test.ts` files that now exercise the real `preflightCheck` activity, which reads this on every call).
10. **Fraud/risk detection is real but honestly limited, the same "illustrative seed list" discipline STEP 15's public-figure check established.** `config/disposable-email-domains.json` is a small, explicitly-labelled illustrative seed (not a comprehensive or maintained block list — a production system needs a subscribed feed). Multi-account detection (`detectMultiAccountSignal`) is a real, genuine signal — Gmail-style dot-folding + universal `+tag` stripping means two emails that normalize to the same identity really are evidence of one person controlling both accounts — but it is narrow: this sandbox has no IP/device-fingerprint infrastructure, so the ABSENCE of a match proves nothing. It is wired into `authRouter.signup` for the disposable-email half only (non-blocking — real-taken, not enforced, since this build has no product requirement to reject disposable-email signups and doing so unilaterally could break legitimate temporary-email testing use). The multi-account half is exposed as a real, tested pure function and an admin-service primitive (`recordRiskSignal`/`listRiskSignals`) but is NOT auto-wired into the signup hot path: `risk_signals.workspace_id` is `NOT NULL` (STEP 1's schema design), and signup happens BEFORE any workspace exists (STEP 5's onboarding creates one afterwards) — there is no workspace to attach a `risk_signals` row to at signup time. Rather than force an awkward NULL-workspace write into a table whose own schema says that should never happen, a detected disposable-email signup is instead recorded to `audit_logs` (which already supports `workspaceId = null` for exactly this "platform-level event, no owning workspace" shape).
11. **Content moderation closes STEP 15's own explicitly-flagged gap** ("No UI for a platform moderator to actually resolve a review"). `resolveModerationReview` (STEP 15, `ugc-service.ts`) had a working implementation with no platform-wide caller and no audit trail; `admin-service.ts`'s `resolveModerationReviewAsAdmin` wraps it with a real `audit_logs` write (the underlying function itself never wrote one), and `listPendingModerationReviews` is this table's first platform-wide (cross-workspace, admin-connection) reader.
12. **A dedicated `packages/core/src/admin/` module holds every pure-logic piece** (feature-flag precedence, disposable-email/multi-account detection), matching the established split between pure domain logic in `packages/core` and real I/O in `apps/web/server/*-service.ts` this build has used since STEP 2.

## A real bug found and fixed during verification

The first draft of `preflightCheck`'s platform-pause read (`apps/worker/src/temporal/activities/publish/preflight.ts`) called `getAdminDb().select(...)` from **inside** the callback passed to `runIdempotentStep` — i.e., while the workspace transaction that function opens (and holds for its whole check-claim-compute-persist sequence, by its own explicit design) was still open. In production this is harmless: `getAdminDb()` and the workspace transaction pool are genuinely separate network Postgres connection pools. In this build's own PGlite test harness, though, `getAdminDb()` (via `setAdminDbForTests`) and the open workspace transaction share the **same single underlying PGlite connection** — nesting a second top-level query through that connection while the transaction was mid-flight was a real, timing-sensitive contention hazard, invisible when a single publish-workflow test file ran alone but reproducing deterministically once all four `publish.workflow.*.test.ts` files (each of which now calls the real `preflightCheck` activity, and so each of which now hits this nested-query pattern) ran together — full-suite `apps/worker` test time went from ~102s to 480–510s, with `TestWorkflowEnvironment.teardown()` failing with `IllegalStateError: Cannot close connection while Workers hold a reference to it` and a cascading timeout in the last file. Root-caused with a real, decisive diagnostic: `git stash` back to the pre-STEP-18 commit reproduced a clean, fast (~148s) pass, confirming this was a genuine STEP 18 regression and not pre-existing flakiness or cross-package `turbo` contention; running just the 4 affected files together (excluding every other apps/worker test file) reproduced the identical failure, isolating it to this exact interaction. Fixed by moving the platform-pause read to *before* `runIdempotentStep` opens its transaction — a strictly better design regardless of the test-harness quirk (an idempotent step should gather its external inputs first, then run its fast transactional claim-compute-persist sequence), not just a workaround. Full apps/worker suite duration after the fix: ~102s, matching the pre-STEP-18 baseline.

## What this step does not do

A comprehensive, maintained disposable-email-domain feed (scope decision 10) — the illustrative seed list is real and tested, not comprehensive, matching STEP 15's public-figure-list precedent exactly. Multi-account detection wired automatically into the signup hot path (scope decision 10) — the pure function and the admin-service primitives are real; the auto-wiring is deliberately not built because `risk_signals` has no pre-workspace home for it. IP/device-fingerprint-based fraud signals — no such infrastructure exists in this sandbox; email-normalization is a real but narrow signal, honestly flagged as such. A dedicated audit-log-export/retention UI beyond the real filtered viewer already built. Policy versioning/appeals for content moderation beyond the real approve/reject flow `moderation_reviews.policy_version` already carries as a column (no UI surface for policy-version history in this pass). A friendlier admin-console UI (raw buttons/inputs, matching the established "functional, not maximally polished" precedent for less-central surfaces since STEP 17's agency console).
